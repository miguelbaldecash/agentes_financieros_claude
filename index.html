6/10 KYC Screener — Evaluacion de Solicitudes

Que hace (v3)

Cruza 2 bases de datos (Aurora PostgreSQL + MySQL CashSys), analiza documentos via OCR, valida identidad con Keynua, consulta Equifax, y evalua contra la politica real extraida de la tabla arbol_decision.

6 dimensiones de analisis
D1 Perfil demograficoEdad, sueldo, ocupacion
D2 Capacidad de pagoRCI vs politica real (arbol decision), pension/sueldo
D3 Historial internoSolicitudes lifetime, ratio rechazo
D4 Documentacion + OCRDocs subidos, OCR parseado, cruce DNI doc vs DNI solicitante
D5 Validacion identidadKeynua (biometrico), verificacion laboral
D6 Controles externosEquifax (central riesgo), arbol de decision, caso especial
Mejoras v1 → v3
OCRv1: contaba existencia → v3: parsea JSON, extrae DNI, cruza vs solicitante
Politicav1: inferida → v3: extraida de arbol_decision (9 reglas reales)
Keynuav1: no analizado → v3: error + DNI mismatch biometrico
Equifaxv1: solo fecha → v3: verifica request_id (llamada real)
IPsv1: intentado (eran del backend) → v3: eliminado

Piloto: 150 solicitudes analizadas

Filtro: sueldo > S/ 500, fuente = boleta de pago (tipo_renta=1), ultimos 12 meses, solicitudes aprobadas/firmadas.

Desestimado Pitch Agent

Que hace

Genera pitch decks y materiales para inversores extrayendo data directamente de la DB. Produce un pitch narrativo (.md) y un deck visual (.html) con graficos interactivos.

Output generado
Pitch narrativoPITCH_BALDECASH_2026.md
Deck visualPITCH_BALDECASH_2026.html (10 slides)
ContenidoExecutive summary, mercado, traccion, NPL, financieros, fondeo, valorizacion, riesgos
Por que se desestimo

El output es tecnicamente correcto pero un pitch para inversores requiere narrativa estrategica, contexto de mercado, y posicionamiento que solo el fundador puede definir. El agente es util como base de datos pero no como autor del pitch.

Conclusiones y Proximos Pasos

Recomendacion

Implementar: KYC Screener (6/10)

Mayor valor inmediato. Cruza 2 DBs, usa politica real, analiza OCR, Keynua, Equifax. FPD 1.7%. Para llegar a 8/10 requiere:

  • Analisis profundo del contenido OCR (monto transferencia vs cuota, fechas, beneficiario)
  • Correlacion estadistica flags → FPD con muestra mas grande (1,000+ casos)
  • Calibrar thresholds del scoring contra defaults reales (logistic regression)
  • Capturar IP real del cliente (actualmente solo se registra IP del backend)
  • Integrar con flujo de aprobacion pre-desembolso (no solo auditoria post)

Evaluar: Statement Auditor + Valuation (4/10)

Utiles como herramientas internas, pero limitados por la calidad de la data contable. Recomendable re-correr despues de la remediacion contable (90 dias).
